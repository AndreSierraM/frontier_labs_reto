01 / Problema
Lo que nadie podía ver

Un servicio crítico del que solo conocíamos sus respuestas.

Sin acceso al código, sin especificación vigente, con clientes reales apoyados encima. El comportamiento había que deducirlo a ciegas, entrada por entrada.

Contrato desfasado v1 ≠ v2

Los 20 ejemplos oficiales describían una versión anterior. En producción el servicio ya aplicaba otras reglas: umbrales distintos, saldo como cadena decimal y bloqueos con otro comportamiento.

Estado invisible

Cuentas, saldos, operaciones y una regla antifraude que no aparecía en ninguna parte. Se descubrió observando: tres transferencias fallidas y la cuenta se bloqueaba.

Sin red de seguridad

Si el original cambiaba una regla, todo lo que dependía de él rompía en silencio. No existía detección, ni corrección, ni evidencia del cambio.

El reto no era copiar. Era reconstruir el contrato observable y sobrevivir a su siguiente cambio.

02 / Reemplazo
Byte a byte

Un reemplazo que no se nota.

El dominio es una máquina de estados pura, separada por completo del transporte HTTP. Mismos status, mismas cabeceras, mismo cuerpo JSON que el original.

Dígito de control

Identificado como ISO 7064 MOD 97-10, el verificador tipo IBAN. Nuestro dataset propio valida 34/34 pares contra el original.

Regla oculta

Tras 3 transferencias fallidas, la cuenta se bloquea con E510. Un depósito posterior la desbloquea. No estaba documentada en ningún sitio.

Contrato exacto

GET /health, POST /msg y POST /__reset; cualquier otra ruta responde 404 E404. Cada respuesta coincide con la del servicio real.

03 / Vigilancia
El servicio que observa al servicio

Si el original cambia, nos enteramos solos.

Un monitor recorre el contrato cada 10 minutos y guarda cada toma. El cambio v2 de nuestro caso se detectó así, automáticamente, sin que nadie lo buscara.

Batería + mapa

31 puntos de contraste en cada corrida y un mapa ampliado de 101 sondas cada hora para descubrir comandos y rutas nuevas.

Evidencia persistida

Snapshots y eventos en Neon Postgres: cada cambio queda con su antes y después, listo para auditar.

Sin ruido

Respeta el rate-limit del original y filtra las muestras de infraestructura, para no confundir un 429 con un cambio real de contrato.

04 / Enjambre
La máquina propone, el humano decide

Cuando detecta un cambio, se adapta.

Una cadena de agentes corre en GitHub Actions ante cada cambio: investiga, parchea, verifica contra el original y abre un pull request. Nunca mergea.

Monitor detecta el cambioDISPARO

La diferencia contra el baseline abre el caso y despierta al enjambre.

Scouts × N investiganPARALELO

Sondean el original desde varios ángulos a la vez para acotar qué regla cambió.

Analista diagnosticaPATCH: SÍ / NO

Decide si hace falta parche y cuál es el alcance. También puede cerrar el caso.

Fixer parcheaCÓDIGO + TESTS + SPEC

Edita el dominio, añade pruebas y actualiza la especificación con la nueva evidencia.

Verificador exige0 DIVERGENCIAS

Compara nuestro reemplazo contra el original. Si hay una sola diferencia, no pasa.

Reporter abre el PRSIN MERGE

Deja el cambio listo para revisión humana. El merge es la única acción manual y dispara el deploy.

▣

Reviewer gate. Si la revisión pide cambios, el enjambre reintenta hasta 2 rondas. El resultado es un pull request con diagnóstico, patch, tests y evidencia — no un despliegue silencioso.
